# Independent review and practical verification

The user explicitly requires careful work, independent review of every deliverable, repeated correction of material findings, and real practical tests. Functionality comes first, followed by clarity, simplicity and measured optimization. This policy applies to documentation, contracts, tooling, prompts, app code, firmware, integrations and demo material.

## Required work cycle

1. Define the intended result and observable acceptance conditions before implementing a coherent change.
2. Produce the smallest clear solution and check it against those conditions.
3. A reviewer other than the author inspects the actual artifact, relevant diff, tests and evidence. A second opinion based only on the author's summary is insufficient.
4. Correct material defects and unjustified complexity. Rerun affected practical checks and return substantive fixes to the reviewer.
5. Close the work only when acceptance passes and the reviewer has no unresolved material finding. Record the evidence, reviewer outcome and any remaining limitation in [the work ledger](12-work-ledger.md).

Review is organized around coherent deliverables and meaningful changes, not a new approval for every command. This avoids multiplying process without improving the result. A late scope change or fix reopens the affected gate. Do not run unchanged tests repeatedly after a clean result unless new evidence creates a reason.

There is no artificial “two reviews and done” rule. The development cycle continues until the required outcome is met or a concrete external blocker remains; repeated failure calls for a different diagnosis. The bounded retries inside the **product's generation service** are a separate mechanism that prevents an invalid app from looping or installing indefinitely. See [execution strategy](05-execution-plan.md).

## Practical evidence by deliverable

| Deliverable | Evidence that matters | Insufficient substitute |
| --- | --- | --- |
| Context and handoff | A fresh agent reconstructs intent/current work; links resolve; all public docs are reachable; new user decisions propagate | More pages or an index that hides stale contradictions |
| Public export | Inspect actual archive members/bytes; exercise secret/link guards with deliberately bad inputs; exclude private source/configuration | Merely creating `.gitignore` or claiming the scanner catches every possible secret |
| Schema and runtime rules | Valid and invalid cases test behavior, references, layout/resource limits and boundaries; shared fixtures govern device and host | A test that reproduces the implementation's assumption without an independent expected outcome |
| Provider integration | Real authenticated request, actual Android media, parsed output/artifact, failure handling and measured elapsed time | Mock success, documentation availability, or a model saying it ran tests |
| Firmware | Build/flash the correct revision, observe real display/touch/timer behavior and recovery on the target board | Successful compilation or a browser simulator |
| Installation | New generated bytes travel to the physical device; matching deployment/hash ACK; repeated delivery and interrupted download behave correctly | HTTP 200 from the backend or a staged package that was never activated |
| One-shot experience | A fresh English request on Android reaches a working app with one action, real partner contribution and no hidden manual repair | Canned app selection, a saved video presented as live or an invisible second approval |
| Reliability | Required recovery/negative cases plus repeated end-to-end runs with timings | Green tests that do not exercise failure paths |
| Optimization | Measured latency, memory or interaction problem improves while acceptance continues to pass | Extra abstractions or speculative tuning with no measured benefit |
| Demo claims | Every claimed working capability has an evidence reference; fallback portions are identified | A polished pitch that promises unimplemented features |

Synthetic malformed inputs are appropriate for testing validators and failure paths. They cannot replace real provider/device tests. Mocks are useful during development, but their results must be labeled and cannot pass the corresponding real-integration gate.

## What reviewers check

Prioritize broken behavior, missing proof, scope drift, incompatible contracts, false success states, exposed private data and complexity that threatens the deadline. Check edge cases that can invalidate the happy path: late taps, missing audio, interrupted download, stale job completion, oversized packages and lost acknowledgments.

Findings state severity, file/behavior, reproduction or missing evidence, expected result and smallest correction. Mark an item as optional when it does not affect acceptance. Do not demand unrelated features to call a review complete. The author fixes; the independent reviewer verifies the fix or explains the remaining gap.

The coordinator remains accountable for integrating all lanes. Hardware/backend/companion approval in isolation does not establish system correctness; [end-to-end acceptance](06-validation-demo.md) is mandatory.

## Honest completion

“Perfect” expresses the desired care, not a provable guarantee about all possible failures. Declare the tested scope, observed results and unresolved conditions. Do not mark a gate passed while required evidence is unavailable, and do not quietly weaken the target to meet the deadline. If access is blocked, record the exact condition and continue independent authorized work.

Before handing off or exporting, keep current status, ownership, decisions and readiness synchronized. The next session should be able to tell what worked, what failed, what was reviewed and what to do next without reading the original conversation.
