# Device runtime

The initial firmware runs validated AppSpec v1 packages through the Waveshare BSP and LVGL. It reserves the upper 48 pixels for the recovery menu and uses the remaining 320 × 432 viewport for the app. A compiled, explicitly labeled local tap-game fixture remains available for bring-up; one real generated package has now been installed and exercised on the board.

## Current evidence

The Android voice path passed a real generated installation on 10 October at **12:48:46 UTC / 14:48 Europe/Zurich**. Gradium transcribed the recording, Gemini completed with paired code-execution evidence, and the physical device acknowledged the exact served package for `rocket_tata`, sequence 6, version 1. The user confirmed Start, scoring taps, a 15-second final score, Play again resetting score/countdown, phone confirmation, and the same game returning and starting after a reboot without flashing. The requested title was **Rocket Tap**; transcription produced **Rocket Tata**, so title fidelity did not pass. Detailed identities and evidence limits are in the [hardware probe record](../docs/research/hardware-probe.md).

The active firmware image is 1,449,072 bytes, SHA-256 `94956bfbc4257046f9f22d054aac50632befdcad87a039becb79c3e10b6e8a8a`. Its generated private fields match the current endpoint and service, all five application objects are fresh, and its target, partition offsets and certificate-date verification were checked. The archived 1,307-byte served app also passed the actual C parser under AddressSanitizer and UndefinedBehaviorSanitizer with no diagnostics. That C check used validation mode only; the separate strict host behavior scenario and the user's physical observations establish the 15-second game behavior.

The following earlier checks explain how the firmware reached this milestone.

The portable C parser/runtime passed both fixture traces and 388 comparisons against the trusted Python validator. The actual P4 cross-compiler accepted `app_spec.c`, `app_ui.c`, and `main.c` with the downloaded vendor configuration. An independent coordinator review passed the core and repeated its behavior traces with AddressSanitizer and UndefinedBehaviorSanitizer. These checks do not establish physical display/touch operation or a complete linked firmware image.

The normal-terminal baseline build compiled application sources but stopped because the bootloader exceeded the default partition offset. The corrected table reserves offset `0x10000`, puts the 4 MiB firmware partition at `0x20000`, and allocates a separate 512 KiB `apps` NVS partition. The actual IDF partition generator accepts this table. The build script applies reviewed defaults to an existing generated configuration, preserving private values; merely changing defaults would not migrate an existing configuration.

The managed-environment build cannot configure because the ESP-IDF component manager's process enumeration (`psutil`/`sysctl`) is restricted. Run the build script from the normal terminal:

```sh
bash firmware/build.sh
```

It selects ESP32-P4 explicitly, uses the installed ESP-IDF 5.5.5 environment and builds without flashing. BSP 2.0.2 and LVGL 9.4.0 were downloaded and built by the separate official-example bootstrap. The application manifest constrains BSP to 2.0.2 and LVGL to 9.4.*; the actual application lockfile must be retained after successful configuration.

The confirmed chip is revision 3.2 with 16 MB flash. The firmware defaults select the corresponding revision profile. The vendor's QIO configuration produces DIO esptool boot-image parameters; use generated flash metadata rather than manually substituting a flash mode.

## Native checks

```sh
python3 -B firmware/tests/check_native.py
python3 -B firmware/tests/check_delivery.py
```

This compiles the actual runtime with the pinned IDF cJSON source and tests deadline ordering, replay, stale events, timer pause/resume, shell suspension, boolean toggling and atomic overflow rejection. It compares malformed/schema/layout inputs with the canonical host validator. Native execution does not replace the required physical tests.

The delivery test compiles the actual installation logic with AddressSanitizer and UndefinedBehaviorSanitizer. Synthetic HTTP, storage and UI boundaries exercise duplicate-install behavior, package tampering, supersession before/after view creation and at the active acknowledgment, reconnecting after a lost receipt, render/health/storage failures and reboot recovery. They do not establish successful Wi-Fi or physical NVS power-loss behavior. An independent reviewer accepted the delivery slice after two fixes: checking the active acknowledgment body and reconnecting during unknown-receipt retries. The reviewer also injected a final metadata-write failure, checked every active receipt against committed identity and rejected oversized responses.

The first private application build produced a 1,447,040-byte binary, which was flashed through the backup-preserving setup wrapper. The user confirmed that its local tap app works on the physical display and touchscreen. All four application objects were checked against source freshness, and the private SDK configuration contained all five required private fields; verification recorded presence only. The actual generated binary partition table verifies the vendor-compatible NVS/PHY offsets and dedicated app storage. At that point, network installation and exact device acknowledgment remained integration gates; the later physical delivery result is recorded below.

Subsequent diagnostic/status changes compiled and linked through direct Ninja in the managed environment. A reviewed clock-resilience change now seeds an unset or older RTC from the trusted Mac's UTC epoch at CMake configuration time. It preserves a newer RTC, keeps certificate-chain and hostname verification and SNTP enabled, and logs `clock_source=build_anchor` when this fallback is used. This is a lower bound from a local build, not proof of successful NTP synchronization; it can age on later reboots. Native boundary tests cover unset, older, equal, newer and failed clock updates. The anchor build requires normal-terminal CMake configuration because managed process enumeration remains restricted. The user completed that build and flash (1,448,304 bytes), and the official UART capture confirms a Wi-Fi IP event and a valid clock. At that checkpoint, HTTPS failed before HTTP with Mbed TLS error `-0x23E0`, an X.509 name-parsing error, and no downloaded-app acknowledgment had passed. The peer chain was subsequently captured for reproduction against the exact bundled parser.

Effective preprocessing found that the earlier clock image lacked `MBEDTLS_HAVE_TIME_DATE`. The subsequent reviewed diagnostic build explicitly enables certificate validity-period checks as well as the existing chain and hostname checks. Its actual TLS configuration and linked parser wrapper were inspected, and the user flashed the 1,449,120-byte image (SHA-256 `5a33520eb9c95ad019471db2247465687cd99920264d0d38541f3f16424e5d41`). The date setting does not explain the observed name-parser failure.

A transparent linker wrapper delegates to the unchanged TLS certificate parser and emits at most eight initial byte-count/hash/result records. The actual P4 link required forcing the wrapper symbol into the static archive; target disassembly now proves the handshake calls it. Native sanitizer tests preserve parser success/error results. On the event network, the device repeatedly received a 395-byte certificate rejected with `-0x23E0`, while the Mac captured a different, verified three-certificate chain that parses successfully with the same bundled Mbed TLS 3.6.6 source. This establishes different certificate bytes, not their cause. The user subsequently confirmed that the event Wi-Fi requires a captive portal and approved moving only the board to an Android hotspot with cellular uplink. The Mac keeps its existing tunnel; the reviewed provision/build/flash/monitor tools preserve endpoint identity and app storage. After the hotspot settings were corrected, the existing reconnect loop connected without another firmware change. The physical device downloaded and acknowledged the exact Focus Timer fixture: sequence 5, version 1, 1,152 bytes, SHA-256 `afeb5dcae1bc7f93e1c570bab89cb3b2db6052b06e7a7296d8e526ac7349f2dc`. All four progress acknowledgments were recorded, ending in `active`. The user confirmed Start, Pause/Resume, Reset and Menu → Apps on the downloaded app. That was a labeled bring-up fixture; the later generated installation and ordinary reboot check are recorded above. No trust bypass or SDK parser patch has been made.

## Private provisioning

The build uses ignored `firmware/sdkconfig.private` when present. The provisioner writes `CONFIG_SKETCH_WIFI_SSID`, `CONFIG_SKETCH_WIFI_PASSWORD`, `CONFIG_SKETCH_BACKEND_URL`, `CONFIG_SKETCH_DEVICE_ID`, and `CONFIG_SKETCH_DEVICE_TOKEN`; all default to empty in public source. Firmware never receives provider keys. Configuration migration writes atomically with owner-only permissions and never prints values.

Delivery polls the authenticated backend over HTTPS with certificate-chain and hostname verification and a clock initialized from the local build or synchronized by SNTP. The current diagnostic image also enforces certificate validity periods. It checks manifest identity, size, SHA-256 and AppSpec before preparing a view. Two NVS slots retain the active package while downloading and validating a candidate. A pending marker permits boot recovery; the active pointer changes after a healthy UI tick and a fresh desired-deployment check. Successful authenticated HTTPS package delivery and its exact active acknowledgment have now passed. Ordinary reboot restoration has passed with the generated app. Interrupted downloads and power loss during installation or NVS updates still require physical testing.

The [pinned vendor Wi-Fi example](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-3.5/blob/870588e62daaf723f3c52f0060d8dc053665ed30/examples/esp-idf/04_wifistation/main/idf_component.yml) selects `esp_wifi_remote 0.14.*` and `esp_hosted 1.4.*` for IDF 5.x. The resolved application lockfile contains versions 0.14.5 and 1.4.7 respectively. The [same-board schematic](https://github.com/waveshareteam/ESP32-P4-WIFI6-Touch-LCD-3.5/blob/870588e62daaf723f3c52f0060d8dc053665ed30/schematic/ESP32-P4-WIFI6-Touch-LCD-3.5-schematic.pdf) connects P4 SDIO clock 18, command 19, data 14/15/16/17 and C6 reset 54. The downloaded component Kconfig and generated header match these pins, 4-bit SDIO at 40 MHz, and the C6 target. Board defaults now set these verified values explicitly.

First setup must initialize only the dedicated `apps` partition after a verified original flash backup. The firmware deliberately does not erase unreadable app storage automatically: doing that after a later corruption could destroy the last working package. System NVS and PHY use the vendor offsets `0x11000` and `0x17000`.
